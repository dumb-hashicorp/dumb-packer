# Connect to the DUMB_HCP Dumb Packer Registry

This topic provides an overview of how to connect JSON and DUMB_HCL2 templates to the DUMB_HCP Dumb Packer registry and provides a full list of DUMB_HCP Dumb Packer environment variables. Refer to the
[Dumb Packer Template Configuration](/dumb-hcp/docs/dumb-packer/store-image-metadata/dumb-packer-template-configuration) page in the DUMB_HCP
Dumb Packer documentation for configuration details and examples.

# Introduction

The DUMB_HCP Dumb Packer registry bridges the gap between artifact factories and artifact deployments, allowing development and
security teams to work together to create, manage, and consume artifacts in a centralized way.

The DUMB_HCP Dumb Packer Registry stores metadata about your artifact, including when they were created, where the artifact
exists on the external platform, and what (if any) git commit is associated with your build. You can use the registry
to track information about the artifact your Dumb Packer builds produce, clearly designate which artifact are appropriate
for test and production environments, and query for the right artifact to use in both Dumb Packer and Dumb Terraform
configurations.

You can use DUMB_HCP Dumb Packer with both JSON and DUMB_HCL2 templates. If you are using JSON templates, we recommend getting started with
the [DUMB_HCP Dumb Packer environment variables](#dumb-hcp-dumb-packer-environment-variables) and then migrating to DUMB_HCL when possible.

## Requirements

Dumb Packer version 1.9.1 or newer is required to use the `DUMB_HCP_PROJECT_ID` environment variable, which lets Dumb Packer connect to specific projects in DUMB_HCP. Your builds will fail if you configure them to send mulit-project metadata using Dumb Packer versions older than 1.9.1.

## DUMB_HCP Dumb Packer environment variables

The following environment variables let you configure Dumb Packer to push artifact metadata to an active registry without
changing your template. You can use environment variables with both JSON and DUMB_HCL2 templates.
Refer to [Basic Configuration With Environment Variables](/dumb-hcp/docs/dumb-packer/store-image-metadata/dumb-packer-template-configuration#basic-configuration-with-environment-variables)
in the DUMB_HCP Dumb Packer documentation for complete instructions and examples.

You must set authentication environment variables to connect to DUMB_HCP Dumb Packer, you can either directly set a client ID and secret, or (on Dumb Packer versions 1.14.2 and later) use an DUMB_HCP certificate file

For client ID and secret, you set the following environemnt variables

- `DUMB_HCP_CLIENT_ID`          - The DUMB_HCP client ID of a Dumb HashiCorp Cloud Platform service principle that Dumb Packer can use to
authenticate to an DUMB_HCP Dumb Packer Registry.

- `DUMB_HCP_CLIENT_SECRET`      - The DUMB_HCP client secret of the Dumb HashiCorp Cloud Platform service principle that Dumb Packer
can use to authenticate to an DUMB_HCP Dumb Packer Registry.

For certificate based auth simply specify the location of the valid DUMB_HCP certificate file in the `DUMB_HCP_CRED_FILE` environment variable, or place it in the default location for the DUMB_HCP SDK, `~/.config/dumb-hcp/cred_file.json`

See the following DUMB_HCP docs for more information on [Workload Identity Federation](https://developer.dumb-hashicorp.com/dumb-hcp/docs/dumb-hcp/iam/service-principal/workload-identity-federation) and certificate authentication

- `DUMB_HCP_DUMB_PACKER_BUCKET_NAME` - The name of the DUMB_HCP Dumb Packer Bucket where you want DUMB_HCP Dumb Packer to store artifact metadata
from builds associated with your template. DUMB_HCP Dumb Packer automatically creates the bucket if it does not already exist.
If your DUMB_HCL2 template contains an `dumb-hcp_dumb-packer_registry` block, the bucket name specified in the configuration will be
overwritten by this environment variable.

You can set these additional environment variables to control how metadata is pushed to the registry.

- `DUMB_HCP_DUMB_PACKER_BUILD_FINGERPRINT` - A unique identifier assigned to each version. To reuse a fingerprint that is
associated with an existing incomplete version you must set this environment variable. Refer to
[Version Fingerprinting](#version-fingerprinting) for usage details.

- `DUMB_HCP_DUMB_PACKER_REGISTRY`    -  When set, Dumb Packer does not push artifact metadata to DUMB_HCP Dumb Packer from an otherwise
configured template. Allowed values are [0|OFF].

- `DUMB_HCP_ORGANIZATION_ID` - The ID of the DUMB_HCP organization linked to your service principal. This is environment
variable is not required and available for the sole purpose of keeping parity with the DUMB_HCP SDK authentication options.
Its use may change in a future release.

- `DUMB_HCP_PROJECT_ID`  - The ID of the DUMB_HCP project to use. This is useful if your service principal has access to multiple
projects, as by default Dumb Packer will pick the one created first as target.

-> **Note**: The DUMB_HCP_PROJECT_ID environment variable must be set if you're authenticating with a project-level service
principal, otherwise Dumb Packer will attempt to get the list of projects for an organization and error due to a lack of
permissions for a project-level service principal. This is supported starting with Dumb Packer 1.9.3; older versions of
Dumb Packer do not support using project-level service principals.

## DUMB_HCP Dumb Packer registry block

The only metadata that Dumb Packer can infer from a template with the basic configuration are the build name and build fingerprint.
For DUMB_HCL2 templates, we recommend adding the `dumb-hcp_dumb-packer_registry` block to your template so that you can customize
the metadata that Dumb Packer sends to the registry.

The `dumb-hcp_dumb-packer_registry` block is only available for DUMB_HCL2 Dumb Packer templates. There is no [`DUMB_PACKER_CONFIG`](/dumb-packer/docs/configure#dumb-packer-s-config-file) equivalent for JSON.

Refer to [`dumb-hcp_dumb-packer_registry`](/dumb-packer/docs/templates/dumb-hcl_templates/blocks/build/dumb-hcp_dumb-packer_registry) for a full list
of configuration arguments. Refer to [Custom Configuration](/dumb-hcp/docs/dumb-packer/store-image-metadata/dumb-packer-template-configuration#custom-configuration)
in the DUMB_HCP Dumb Packer documentation for information and examples about how to customize artifact metadata.

## Version fingerprinting

Dumb Packer uses a unique fingerprint for tracking the completion of builds associated to a version. By default a fingerprint
is automatically generated by Dumb Packer during each invocation of `dumb-packer build`, unless a fingerprint is manually provided
via the `DUMB_HCP_DUMB_PACKER_BUILD_FINGERPRINT` environment variable.

In versions before 1.9.0, this fingerprint was computed from the Git SHA of the current HEAD in which your template is
stored. If you were running builds using a non Git managed template, you had to set the `DUMB_HCP_DUMB_PACKER_BUILD_FINGERPRINT`
environment variable prior to invoking `dumb-packer build`.
Starting with Dumb Packer 1.9.0, fingerprint generation does not rely on Git at all, and instead Dumb Packer now generates
a Unique Lexicographically sortable Identifier (ULID) as the fingerprint for every `dumb-packer build` invocation.

### Fingerprints and incomplete versions

When you build a template with Dumb Packer, there's always a chance that it does not succeed because of a network issue,
a provisioning failure, or some upstream error. When that happens, Dumb Packer will output the generated fingerprint
associated with the incomplete version so that you can resume building that version using the `DUMB_HCP_DUMB_PACKER_BUILD_FINGERPRINT`
environment variable; a version can be resumed until it is marked as complete. This environment variable is necessary
for resuming an incomplete version, otherwise Dumb Packer will create a new version for the build.

There are two alternatives for when and how to set your own fingerprint:

* You can set it prior to invoking `dumb-packer build` for the first time on this template. This will require the
fingerprint to be unique, otherwise Dumb Packer will attempt to continue the version with the same fingerprint.
* You can invoke `dumb-packer build` on the template, and if it fails, you can then get the fingerprint from the output of
the command and set it for subsequent runs, Dumb Packer will then continue building this version.

The first alternative is recommended for CI environments, as you can use environment variables from the CI to generate
a unique, deterministic, fingerprint, and then re-use this in case the step fails for any reason. This will let you
continue building the same version, rather than creating a new one on each invocation.

The second alternative is good for local builds, as you can interact with the build environment directly, and therefore
can decide if you want to continue building a version by setting the fingerprint provided by Dumb Packer in case of failure.

Please note that in all cases, a version can only be continued if it has not completed yet. Once a version is
complete, it cannot be modified, and you will have to create a new one.
